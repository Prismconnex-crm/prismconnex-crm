# People Explorer — filters, local assistant, results

**Date:** 2026-08-01
**Status:** Approved for planning
**Supersedes:** `2026-08-01-people-instant-query-parser-design.md`

## Problem

The People page (`/app/people`) does not match the Companies and Events pages, and
none of it is wired.

Verified against the code on disk:

1. `components/crm/people-section.tsx` is a 462-line component with a horizontal
   five-control filter bar above a results table and a person-detail card pinned
   in an `xl:grid-cols-[1fr_360px]` right column. All five controls are static
   `<button>` elements with hardcoded labels.
2. The page renders 7 hardcoded mock contacts. The string `2,418` occurs exactly
   once in the repository — as a label at `people-section.tsx:49`. It counts
   nothing.
3. The Prisma `Contact` model (`prisma/schema.prisma:193`) carries only
   `firstName, lastName, email, title, verified`.
4. No local query parser exists. `lib/events/` contains `chips.ts` and
   `filters.ts` only; Events still calls `/api/ai/event-query` →
   `extractEventFilters` (`services/ai-event-query.service.ts:104`), a
   `claude-opus-5` call requiring `ANTHROPIC_API_KEY`.

The predecessor spec addressed 1–4 but specified a search box that emits filters
and chips only. A subsequent HTML prototype ("People Explorer") re-scoped the
page around a conversational assistant panel that also summarises the dataset
and finds duplicates. This spec reconciles the two; where they conflict, the
prototype wins unless noted.

## Goal

Typing *"verified marketing managers in Germany with 80%+ confidence"* fills the
result list immediately — no network round trip, no API key — and the assistant
replies in prose composed from the parse result and the matched rows. The left
rail ticks itself to match what was read.

Explicitly **out of scope**: implementing the Events parser, obtaining an API
key, persisting contacts to Postgres, and wiring the bulk actions.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Assistant answers | Conversational, **locally generated** | The prototype's thread UI is kept, but every sentence is template-composed from `ParsedQuery` + filtered rows. Zero network calls, zero `ANTHROPIC_API_KEY`, synchronous. Reverses the predecessor spec's "no `answer` field". |
| Answer representation | Structured `Answer` object, not HTML strings | The prototype builds HTML by concatenation and injects it with `insertAdjacentHTML`. In React that would need `dangerouslySetInnerHTML` and could not be unit-tested. |
| Layout in query state | Hero Ask card collapses to a sticky one-line bar | The prototype's 392px Ask card puts the first result row ~700px down. Collapsing on query restores the "first row visible at 1366×768" requirement without changing the empty state. |
| Facet model | Full model in data and parser; six facets visible, five behind "More filters" | Keeps the rail as clean as the prototype draws it without losing the parse precision that makes `marketing managers` two constraints instead of one. |
| Multi-turn behaviour | Each ask **replaces** the filter state | What the prototype does (`F = {...f}`). The chips always explain the visible result; manual sidebar edits cover refinement. |
| Contact data | Static `data/people-seed.json`, generated by a committed script | Mirrors `data/find-shows-seed.json`. No migration, no Postgres dependency, no tenancy question — a workspace-scoped `Contact` table would make the count vary per workspace, so "2,418 contacts" could not be a fixed header. |
| Shared parser code | New `lib/search/`, People-specific code in `lib/people/` | Events must stay untouched. Generic pieces — normalize, n-gram phrase matching, Levenshtein, numeric-condition scanning — go in `lib/search/` so Events can adopt them later without a second implementation. |
| Leftover-keyword search | Hand-written inverted index in `lib/search/textScore.ts` | MiniSearch is not installed and `CLAUDE.md` forbids installing dependencies unless explicitly asked. At 2,418 records over 4 fields a weighted inverted index is equivalent and ~50 lines. |
| Where filtering runs | Pure core, imported by the client **and** wrapped by the route | The client path gives zero-latency typing and instant facet recounts. Cost is ~150 KB gzipped of seed JSON in the bundle. |
| Person detail | Persistent 330px right column inside the results card | What the prototype draws. Reverses the predecessor spec's slide-over drawer; `components/ui/drawer.tsx` is left untouched. |

## Data

### Generator — `scripts/generate-people-seed.mjs`

Deterministic: a seeded PRNG (mulberry32, fixed seed) so re-running produces a
byte-identical file. Writes `data/people-seed.json` with exactly 2,418 records.
The file is committed; the script exists so distributions can be adjusted, not
because anyone needs to run it. It writes only to `data/` — no temp files, no
large intermediates (see the disk-space constraint in `CLAUDE.md`).

The prototype's **16 contacts are emitted verbatim as the first records**, with
the new fields filled in consistently. They replace the 7 previously hardcoded
in `people-section.tsx`. This matters beyond familiarity: the pair Sarah Miller
(`sarah@novaai.example`, verified, 91%) and Sara Millar
(`s.miller@novaai.example`, needs verify, 62%) is the fixture the duplicate
finder is tested against.

### Record shape — `types/people.ts`

```ts
export type Person = {
  id: string;
  firstName: string; lastName: string; name: string;
  title: string;                 // "Marketing Manager"
  seniority: Seniority;          // closed vocabulary
  department: Department;        // closed vocabulary
  company: string; companyDomain: string;
  email: string | null; phone: string | null; linkedin: string | null;
  country: string; city: string;
  source: Source;
  verification: 'verified' | 'needs_verify' | 'unverified';
  confidence: number;            // 0-100
  score: number;                 // platform score, 0-100
  starred: boolean;
  fetchedAt: string;             // ISO YYYY-MM-DD
  lastActive: string;            // display string, e.g. "2h ago"
  avatar: string;                // single initial
  searchText: string;            // precomputed, normalized
};

export type Seniority = 'C-Level' | 'VP' | 'Director' | 'Manager' | 'Individual Contributor';

export type Department =
  | 'Marketing' | 'Sales' | 'Engineering' | 'Product' | 'Partnerships'
  | 'Procurement' | 'HR' | 'Finance' | 'Operations';

export type Source = 'User import' | 'Licensed dataset' | 'Web enrichment';
```

Three reconciliations against the predecessor spec:

- **Sources** are the prototype's three exactly. `Event scan` and `Partner feed`
  are dropped; the header strip already reads "User import / Licensed dataset".
- **`starred`** is a real boolean (~12% of records), correlated with `score >= 88`
  so the star rendered beside the Platform Score stays coherent with the number.
- **"Leadership" is not a department.** The prototype's `ROLE_LABEL` maps
  `executive → Leadership`, but two of its own rows contradict that: Ahmed Farouk
  is "Operations Director" and Elena Rossi is "Founder & CEO" — a *seniority*
  distinction. So `department` carries the nine values above, the rail's **"Job
  function" accordion is the department facet**, and `leadership` / `executive` /
  `exec` / `c-level` are aliases onto **seniority `C-Level`**. Every query the
  prototype answers still answers.

### Distributions

Chosen so every acceptance query returns a non-trivial set and no single facet
dominates:

- **Countries** — ~28 values drawn from the Events country vocabulary, weighted
  toward Germany, United States, United Kingdom, France, India, Netherlands,
  United Arab Emirates. At least 120 contacts in Germany and 90 in India.
- **Companies** — ~140 names including the prototype's eight. Each company has
  one country and 4–40 contacts, so `company` behaves like a real facet.
- **Seniority** — C-Level 8%, VP 12%, Director 20%, Manager 34%, IC 26%.
- **Department** — Marketing and Sales weighted highest, the other seven even.
- **Title** — composed from seniority + department so `title`, `seniority` and
  `department` never contradict each other (`Marketing Manager`, `VP of Sales`,
  `Head of Partnerships`, `Product Lead`). ~60 distinct titles.
- **Verification** — verified 58%, needs_verify 27%, unverified 15%.
  `unverified` implies `email === null`.
- **Confidence** — 40–99, mean ≈ 84 (matching the "Avg. Confidence 84%" in the
  header strip).
- **Contactability** — 85% have an email (all `verified` do), 46% a phone, 61% a
  LinkedIn URL.
- **Near-duplicates** — 12 deliberate pairs beyond Miller/Millar, spread across
  the three detection rules below, plus 6 decoys: distinct people at the same
  company with similar-but-not-matching names, which must **not** be flagged.

The generator asserts the resulting counts against these bands and exits
non-zero if any is out, so a future tweak cannot silently empty a test.

## Filters

```ts
export type PeopleFilters = {
  countries: string[]; cities: string[]; companies: string[];
  titles: string[]; seniorities: string[]; departments: string[];
  sources: string[]; verification: ('verified'|'needs_verify'|'unverified')[];
  confidenceMin: number | null; confidenceMax: number | null;
  scoreMin: number | null; scoreMax: number | null;
  hasEmail: boolean | null; hasPhone: boolean | null; hasLinkedIn: boolean | null;
  starred: boolean | null;
  band: 'all' | 'high' | 'needs';
  ids: string[] | null;
  keywords: string[];
};
```

Values within a field are OR-ed, fields are AND-ed. `keywords` is the exception —
every term must match, consistent with `lib/events/filters.ts:183`.

The contactability flags and `starred` are **tri-state**. `null` means unset;
`false` is a real constraint (`no email`) distinct from it. The URL codec must
round-trip all three states. The rail's three *quick chips* only ever toggle
between `null` and the positive value — the `false` state is reachable from the
Contactability toggles under "More filters", and from a parsed query
(`contacts with no phone`).

Two fields exist because of the prototype:

- **`band`** backs the `All` / `High confidence` (≥85) / `Needs verification`
  pills above the table. The prototype applies these outside its filter object,
  which makes them invisible to the chips and to the match count. Here they are
  a normal filter dimension: they compose with everything else, produce a chip,
  and serialise into the URL, so a shared link reproduces what was on screen.
- **`ids`** pins the table to an explicit record set. Only the duplicates answer
  sets it. The prototype fakes this with `text: "miller"`, which works only
  because its sample set is 16 rows; over 2,418 it would drag in every Miller in
  the file.

## `lib/search/` — shared, domain-free

| File | Exports |
|---|---|
| `normalize.ts` | `normalize(s)` — lowercase, NFD accent strip, punctuation→space, collapse whitespace. `tokenize(s)` → `Token[]` carrying `{ text, start, end }` offsets into the normalized string. |
| `phrase.ts` | `buildPhraseIndex(entries: PhraseEntry[])`, `matchPhrases(tokens, index)` → `{ matches, remaining }`. |
| `fuzzy.ts` | `levenshtein(a, b, max)` — bounded, early-exits above `max`. `fuzzyFind(token, index)`. |
| `numeric.ts` | `scanNumericConditions(tokens, specs)` → `{ conditions, remaining }`. |
| `stopwords.ts` | `STOPWORDS: ReadonlySet<string>`. |
| `textScore.ts` | `buildTextIndex(docs, fields)`, `scoreQuery(index, terms)` → ranked ids. |
| `types.ts` | `Match = { field: string; value: string; sourceText: string }`, `Token`, `ParsedQuery<F>`. |

`normalize` here is deliberately **not** the one in `lib/events/filters.ts:17`,
which strips case and accents but leaves punctuation. Hyphens and periods must
become separators for `c-level`, `v.p.` and `co-founder` to tokenize. Events
keeps its own; nothing there changes.

### Phrase matching

`matchPhrases` walks the token array left to right. At each position it tries
n-grams longest-first — 4, then 3, then 2, then 1 — and on a hit records the
match, advances past the consumed span, and continues. Within a single n-gram
length, ties break by insertion order of the index, so the caller controls
precedence by build order.

Each n-gram is tried twice: verbatim, then **depluralised** — trailing `s` or
`es` stripped from every word in the gram. This is what makes `marketing
managers` and `sales directors` resolve; a separate stemming stage would have to
run before phrase matching and would then corrupt company names.

A `PhraseEntry` may carry more than one `{ field, value }` pair, which is how a
combined title phrase yields two matches from one span.

## `lib/people/`

### `aliases.ts`

- Countries reuse the Events country vocabulary and its aliases (`uk` → United
  Kingdom, `us`/`usa` → United States, `deutschland` → Germany, `uae` → United
  Arab Emirates).
- `COMBINED_TITLE_PHRASES` — each entry emits **both** a department and a
  seniority: `marketing manager`, `sales director`, `vp marketing`, `vp of
  marketing`, `head of partnerships`, `product lead`, and the systematic
  cross-product of the two closed vocabularies (`<department> <seniority>` and
  `head of <department>`), so the table stays in sync by construction rather
  than by hand.
- `SENIORITY_ALIASES` includes `leadership`, `executive`, `exec`, `c-level`,
  `c level`, `founder`, `ceo`, `cto`, `cfo` → `C-Level`.
- `VERIFICATION_PHRASES` and `BOOLEAN_PHRASES` — `verified` / `clean` / `safe to
  send`; `needs verification` / `unverified` / `not verified` / `risky` /
  `bounce`; `with email` / `no phone` / `has linkedin`; `starred` / `favourite`
  / `favorite`.

### `vocabulary.ts`

`buildPeopleVocabulary(people)` — memoised at module level. Builds one
`PhraseIndex` from, in this insertion order (earlier wins ties at equal length):

1. combined title phrases (both fields)
2. verification and boolean phrases
3. seniority aliases
4. department aliases
5. country aliases and `SELECT DISTINCT country`
6. `SELECT DISTINCT company`
7. `SELECT DISTINCT title`
8. `SELECT DISTINCT city`
9. `SELECT DISTINCT source`

Company before title before city matters: `NovaAI Systems`, `CloudForge Ltd` and
`Medidata Europe` must win over any single word inside them, and longest-first
already guarantees that against shorter entries.

### `parse-query.ts`

```ts
export function parsePeopleQuery(input: string, vocab: Vocabulary): ParsedQuery
// ParsedQuery = { filters: PeopleFilters, matched: Match[], unmatched: string[], intent: Intent }
// Intent = 'search' | 'summary' | 'duplicates'
```

Pure, synchronous, no I/O, never throws. Input capped at 500 characters.

**Stage 0 — intent.** `duplicate` / `dedupe` / `merge` → `duplicates`. `how
many` / `count` / `breakdown` / `summarise` / `summarize` / `overview` with no
other dimension matched → `summary`. Otherwise `search`. `duplicates` beats
`summary`.

**Stage 1 — normalize.** `normalize()` then `tokenize()`. Every later stage
operates on this single token array and consumes token spans from it; there is
no re-parsing of raw text downstream.

**Stage 2 — numeric conditions.** `scanNumericConditions` against two field
specs (`confidence`, and `score` with the alias `platform score`). Handles `%`,
`+`, `>`, `>=`, `<`, `<=` and above / over / more than / at least / greater than
/ below / under / at most, plus `between X and Y`. The bare-adjective forms are
separate phrase entries: `high confidence` → `confidenceMin: 85`, `low
confidence` → `confidenceMax: 60`, and `top rated` / `top scoring` / `best` /
`high score` → `scoreMin: 90`. Matched spans are consumed.

Runs **before** phrase matching so the word `confidence` in *"confidence above
80"* is eaten by the numeric scanner rather than surviving to keywords.

**Stage 3 — boolean flags.** Verification, starred and contactability phrases,
consumed. `needs verification` / `unverified` / `not verified` set **both**
`needs_verify` and `unverified`.

Verification and contactability are independent, and the longer phrase wins:
`verified emails` sets `verification: ['verified']` **only** — it does not also
set `hasEmail`, because the whole two-word span is consumed by the verification
entry before `email` can be read as a contactability signal. `with email` sets
`hasEmail: true` only.

**Stage 4 — phrase match.** `matchPhrases` over the remaining tokens, 4-gram
first. This stage must run before keywords — the Events bug where `united
kingdom` fell through as two separate keywords is exactly this ordering failure.

**Stage 5 — stopword removal** from what remains.

**Stage 6 — fuzzy rescue.** Single tokens only, against the 1-gram entries of
the vocabulary. Accepted when Levenshtein distance ≤ 2 **and** ≤ 25% of the
token's length. Single-token rescue is sufficient for the multi-word cases:
`markting managrs germny` rescues `marketing` (distance 1 of 9), `managrs` →
`manager` (1 of 7) and `germny` → `germany` (1 of 7) independently, and
`marketing` alone maps to department Marketing while `manager` alone maps to
seniority Manager. No fuzzy phrase matching is needed.

**Stage 7 — leftovers to keywords.** Whatever survives, deduplicated, capped at
3, also returned as `unmatched`.

### `filters.ts`

Mirrors `lib/events/filters.ts` in structure:

- `parsePeopleQueryState(search)` / `serializePeopleQueryState(state)` — the URL
  is the single source of truth shared by rail, ask panel and table. Params:
  `country`, `city`, `company`, `title`, `seniority`, `department`, `source`,
  `verify`, `id`, `keyword` (repeatable); `confmin`, `confmax`, `scoremin`,
  `scoremax`; `email`, `phone`, `li`, `star` (`1`/`0`, absent = null); `band`,
  `q`, `sort`, `page`.
- `buildChecks(filters, search)` — one predicate per dimension, returning `null`
  for an unconstrained dimension.
- `filterPeopleList(people, filters, search)`.
- `computePeopleFacets(people, filters, search)` — counts each dimension against
  every check **except its own**, so opening "Country" still shows every
  reachable country. Same hold-one-out approach as `computeEventFacets`.
- `widenSuggestions(people, filters, search)` — for each constrained dimension,
  the count with that one dimension dropped. Returns the dimension whose removal
  recovers the most records. Reuses the hold-one-out machinery; consumed by the
  `empty` answer.
- `sortPeople(people, sort)` — `score` (default, descending), `confidence`,
  `name` (A–Z), `fetched` (most recent first). All sorts break ties on `id` so
  paging is stable.

### `search-index.ts`

Module-level array loaded from the seed at first access and cached across
requests; `revalidatePeopleIndex()` clears it for a future import path.
`queryPeople({ filters, search, sort, page })` → `{ results, total }`,
paginated at 25 (matching the table footer) with the true total returned
separately.

### `chips.ts`

`buildPeopleFilterChips(filters, search)` → `{ id, label, value }[]`, and
`removePeopleFilterChip(filters, search, chipId)`. Structurally compatible with
`QueryChip` in `components/search/filter-chips.tsx`, matching
`lib/events/chips.ts`. Numeric chips read `≥ 80%` / `≤ 50%` / `70–90%`;
tri-state chips read `Has work email` / `No work email`; `band` reads `High
confidence` / `Needs verification` and is absent when `all`.

### `duplicates.ts`

`findDuplicatePairs(people, limit = 10)` → `DuplicatePair[]`.

Blocking: group by exact `company` — ~140 blocks averaging ~17 records, so
~19,000 comparisons worst case. Fast enough to run synchronously on demand; not
precomputed, so it stays correct if the index is ever revalidated.

A pair is flagged when **any** rule fires:

1. Bounded Levenshtein ≤ 2 on the normalized full name.
2. Identical email local-part after stripping dots, hyphens and underscores
   (`sarah` vs `s.miller` do not match; `s.miller` vs `smiller` do).
3. Same surname **and** same first initial **and** different given name.

Rule 3 is the one that risks false positives, so it additionally requires the
two records to share a `department`. The six seeded decoys exercise this.

Each pair carries `{ keepId, mergeId, rule, nameDistance, confidenceGap }`.
`keepId` is the higher-confidence record; ties break on `verification` rank then
`score`. Ranked by `nameDistance` ascending, then `confidenceGap` descending.

### `answer.ts`

```ts
export type AnswerSegment = { type: 'text' | 'em'; value: string };

export type AnswerAction =
  | { kind: 'sequence'; label: string; count: number }
  | { kind: 'verify';   label: string; count: number }
  | { kind: 'save';     label: string }
  | { kind: 'export';   label: string }
  | { kind: 'merge';    label: string; keepId: string; mergeId: string }
  | { kind: 'keep-both'; label: string }
  | { kind: 'clear';    label: string };

export type Answer = {
  kind: 'results' | 'empty' | 'unparsed' | 'summary' | 'duplicates';
  segments: AnswerSegment[];
  previewIds: string[];      // <= 4
  totalCount: number;
  actions: AnswerAction[];
};

export function buildAnswer(input: {
  parsed: ParsedQuery; rows: Person[]; total: number; people: Person[];
}): Answer;
```

Pure, synchronous, returns no HTML. `em` segments are the bold-indigo runs the
prototype writes as `<b>`; the renderer maps them to a `<strong>`, so no
`dangerouslySetInnerHTML` appears anywhere.

Five kinds:

- **`results`** — count, verified count, average confidence, and a closing
  sentence that either warns about the unverified subset or states the set is
  safe to send to. Actions: `sequence` (count = rows), `save`, and `verify`
  (count = the unverified subset) — `verify` is omitted entirely when that
  subset is empty, so no action ever offers to act on zero records.
- **`empty`** — filters parsed but nothing matched. Names the single most
  restrictive constraint from `widenSuggestions` and the exact number dropping
  it recovers: *"Nothing matches. Dropping the 80% confidence floor brings back
  14."* The prototype's version of this branch contains a filter callback whose
  body is `return true`, so it always reports "a few" regardless of the data;
  that is rebuilt, not ported. Action: `clear`.
- **`unparsed`** — nothing recognised. Reproduces the prototype's guidance copy
  naming the five dimensions and giving an example. No actions.
- **`summary`** — total, verified/unverified split, average confidence, the top
  five countries by count, and the largest department. Computed over `people`,
  not `rows`. Actions: `verify`, `export`.
- **`duplicates`** — pair count, then the top pair described in full (both
  names, shared title and company, the two confidences and sources, and which to
  keep). `previewIds` is the flattened top pairs; the caller sets `filters.ids`
  to the same set. Actions: `merge`, `keep-both`, `save`.

## API — `app/api/people/query/route.ts`

```
POST { prompt: string, filters?: PeopleFilters, sort?: string, page?: number }
200  { filters, matched, unmatched, intent, answer, results, total, tookMs }
```

A thin controller over the pure modules: `validateBody()` with a Zod schema in
`models/people-query.ts`, then `parsePeopleQuery` → `queryPeople` →
`buildAnswer`, then `jsonOk`. No tenancy — like `/api/companies`, this is a
shared discovery dataset, not workspace data. Uses `UnauthorizedError` from
`lib/http/errors.ts` if auth is later added, per the gotcha in `CLAUDE.md`.

No `fetch` to any external service. No reference to `ANTHROPIC_API_KEY` anywhere
in the path. The route exists for parity and for future server-side use; the UI
imports the same pure modules directly so typing stays instant.

### Results

Company, Work email, Status badge, Confidence (number + bar). Row click selects;

matching what the page shows today.

The bulk bar (Select all, Verify emails, Add to Sequence, Merge, `N selected`)
sits above the table and gains **Select all N matching**. Selection is held as
`{ mode: 'page' | 'all', ids: Set<string> }` so "all matching" survives paging.
Changing any filter clears the selection.

The detail pane is a persistent 330px right column inside the results card,
rendering avatar, name, company tag, Add to CRM / Add to Sequence, work email
with status badge, country, phone, title, and the source/fetched/confidence/score
block. It falls back to the first row when the selection leaves the filtered set.

### Visual language

Tailwind with the repo's tokens, not the prototype's CSS: `rounded-[12px]` /
`rounded-[14px]`, `border-slate-200 dark:border-[#22304A]`, `dark:bg-[#111B2E]`,
bracketed font sizes, the indigo→fuchsia gradient accent, `Verified` emerald and
`Needs verify` amber badges. The prototype is light-only; every surface here
gets its dark token.
