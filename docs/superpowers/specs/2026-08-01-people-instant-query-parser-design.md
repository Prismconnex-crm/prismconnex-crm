# Instant contact search on the People page (no model call)

**Date:** 2026-08-01
**Status:** Approved for planning

## Problem

The People page (`/app/people`) does not match the Companies and Events pages.

Verified against the code on disk:

1. **The layout is wrong.** `components/crm/people-section.tsx` is a 462-line
   component with a horizontal five-control filter bar (Search / Country /
   Source / Verification / Confidence) above a results table, and a
   person-detail card permanently pinned in a `xl:grid-cols-[1fr_360px]` right
   column. There is no filter sidebar and no natural-language search. None of
   the five controls are wired — every one is a static `<button>` with a
   hardcoded label.

2. **There is no contact data.** The page renders 7 hardcoded mock contacts
   (`people-section.tsx:24`). The string `2,418` occurs exactly once in the
   entire repository — as a label at `people-section.tsx:49`. It is not a count
   of anything.

3. **The Prisma `Contact` model cannot express the requirement.**
   `prisma/schema.prisma:193` carries only `firstName, lastName, email, title,
   verified`. The sidebar and parser need country, city, phone, LinkedIn,
   seniority, department, source, confidence, platform score and fetched date —
   none of which exist.

4. **The parser this page was meant to reuse does not exist either.**
   `lib/events/` contains `chips.ts` and `filters.ts` only. There is no
   `parseQuery.ts`, `vocabulary.ts`, `aliases.ts` or `searchIndex.ts`. Events
   still calls `/api/ai/event-query` → `extractEventFilters`
   (`services/ai-event-query.service.ts:104`), which is a `claude-opus-5` call
   requiring `ANTHROPIC_API_KEY`. A local parser for Events is specified in
   `docs/superpowers/specs/2026-08-01-events-instant-query-parser-design.md`
   but is unimplemented.

## Goal

Typing a sentence like *"verified marketing managers in Germany with 80%+
confidence"* into the People page fills a result list immediately — no network
round trip, no API key, no prose answer. The left sidebar ticks itself to match
what was read.

Explicitly **out of scope**: implementing the Events parser, obtaining an API
key, and persisting contacts to Postgres.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Contact data | Static `data/people-seed.json`, generated by a committed script | Mirrors `data/find-shows-seed.json`, the pattern already used for the only other large static dataset. No migration, no Postgres dependency, no tenancy question (a workspace-scoped `Contact` table would make the count vary per workspace, so "2,418 contacts" could not be a fixed header). |
| Shared parser code | New `lib/search/`, People-specific code in `lib/people/` | Events must stay untouched (acceptance criterion). Generic pieces — normalize, n-gram phrase matching, Levenshtein, numeric-condition scanning — go in `lib/search/` so Events can adopt them later without a second implementation. |
| Leftover-keyword search | Hand-written inverted index in `lib/search/textScore.ts` | MiniSearch is not installed, and `CLAUDE.md` forbids installing dependencies unless explicitly asked. At 2,418 records over 4 fields a weighted inverted index is equivalent in behaviour and ~50 lines. |
| Where filtering runs | Pure core, imported by the client **and** wrapped by the route | The client path gives zero-latency typing and instant facet recounts on every checkbox. `app/api/people/query/route.ts` is still built to the specified contract, wrapping the same pure modules. Cost is ~150 KB gzipped of seed JSON in the bundle. |
| Person detail | Slide-over drawer, extending `components/ui/drawer.tsx` | A right-side drawer with backdrop dismiss already exists. It needs Esc handling and a width override; widening it beats writing a second one. |

## Data

### Generator — `scripts/generate-people-seed.mjs`

Deterministic: a seeded PRNG (mulberry32, fixed seed) so re-running produces a
byte-identical file. Writes `data/people-seed.json` with exactly 2,418 records.
The file is committed; the script exists so distributions can be adjusted, not
because anyone needs to run it.

The 7 contacts currently hardcoded in `people-section.tsx` (Sarah Miller /
NovaAI Systems, David Lee / CloudForge Ltd, Amina Khan / Medidata Europe, Jonas
Richter, Mia Thompson, Luca Romano, Elena Silva) are emitted verbatim as the
first records, with the new fields filled in consistently. This keeps the
worked example and the `"verified contacts at NovaAI Systems"` test anchored to
rows a reader can recognise.

### Record shape — `types/people.ts`

```ts
export type Person = {
  id: string;
  firstName: string; lastName: string; name: string;
  title: string;                 // "Marketing Manager"
  seniority: Seniority;          // closed vocabulary
  department: Department;        // closed vocabulary
  company: string; companyDomain: string;
  email: string | null; phone: string | null; linkedin: string | null;
  country: string; city: string;
  source: string;                // "User import" | "Licensed" | "Event scan" | "Partner feed"
  verification: 'verified' | 'needs_verify' | 'unverified';
  confidence: number;            // 0-100
  score: number;                 // platform score, 0-100
  fetchedAt: string;             // ISO YYYY-MM-DD
  lastActive: string;            // display string, e.g. "2h ago"
  avatar: string;                // single initial
  searchText: string;            // precomputed, normalized
};

export type Seniority = 'C-Level' | 'VP' | 'Director' | 'Manager' | 'Individual Contributor';
export type Department =
  | 'Marketing' | 'Sales' | 'Engineering' | 'Product'
  | 'Partnerships' | 'HR' | 'Finance' | 'Operations';
```

### Distributions

Chosen so every acceptance query returns a non-trivial set, and so no single
facet dominates:

- **Countries** — ~28 values drawn from the Events country vocabulary, weighted
  toward Germany, United States, United Kingdom, France, India, Netherlands,
  United Arab Emirates. At least 120 contacts in Germany and 90 in India.
- **Companies** — ~140 names, including the five real ones above. Each company
  has one country and 4–40 contacts, so `companies` behaves like a real facet.
- **Seniority** — C-Level 8%, VP 12%, Director 20%, Manager 34%, IC 26%.
- **Department** — Marketing and Sales weighted highest, the other six even.
- **Title** — composed from seniority + department so `title`, `seniority` and
  `department` never contradict each other (`Marketing Manager`, `VP of Sales`,
  `Head of Partnerships`, `Product Lead`). ~60 distinct titles.
- **Verification** — verified 58%, needs_verify 27%, unverified 15%.
  `unverified` implies `email === null`.
- **Confidence** — 40–99, mean ≈ 84 (matching the "Avg. Confidence 84%" already
  shown in the header strip).
- **Contactability** — 85% have an email (all `verified` do), 46% a phone, 61% a
  LinkedIn URL.

The generator asserts the resulting counts against these bands and exits
non-zero if any is out, so a future tweak cannot silently empty a test.

## Filters

```ts
export type PeopleFilters = {
  countries: string[]; cities: string[]; companies: string[];
  titles: string[]; seniorities: string[]; departments: string[];
  sources: string[]; verification: ('verified'|'needs_verify'|'unverified')[];
  confidenceMin: number | null; confidenceMax: number | null;
  scoreMin: number | null; scoreMax: number | null;
  hasEmail: boolean | null; hasPhone: boolean | null; hasLinkedIn: boolean | null;
  keywords: string[];
};
```

Values within a field are OR-ed, fields are AND-ed. `keywords` is the exception
— every term must match, consistent with `lib/events/filters.ts:183`.

The three contactability flags are **tri-state**. `null` means unset; `false`
is a real constraint (`no email`) and is distinct from it. The URL codec must
round-trip all three states.

## `lib/search/` — shared, domain-free

| File | Exports |
|---|---|
| `normalize.ts` | `normalize(s)` — lowercase, NFD accent strip, punctuation→space, collapse whitespace. `tokenize(s)` → `Token[]` carrying `{ text, start, end }` offsets into the normalized string. |
| `phrase.ts` | `buildPhraseIndex(entries: PhraseEntry[])`, `matchPhrases(tokens, index)` → `{ matches, remaining }`. |
| `fuzzy.ts` | `levenshtein(a, b, max)` — bounded, early-exits above `max`. `fuzzyFind(token, index)`. |
| `numeric.ts` | `scanNumericConditions(tokens, specs)` → `{ conditions, remaining }`. |
| `stopwords.ts` | `STOPWORDS: ReadonlySet<string>`. |
| `textScore.ts` | `buildTextIndex(docs, fields)`, `scoreQuery(index, terms)` → ranked ids. |
| `types.ts` | `Match = { field: string; value: string; sourceText: string }`, `Token`, `ParsedQuery<F>`. |

`normalize` here is deliberately **not** the one in `lib/events/filters.ts:17`,
which strips case and accents but leaves punctuation. Hyphens and periods must
become separators for `c-level`, `v.p.` and `co-founder` to tokenize. Events
keeps its own; nothing is changed there.

### Phrase matching

`matchPhrases` walks the token array left to right. At each position it tries
n-grams longest-first — 4, then 3, then 2, then 1 — and on a hit records the
match, advances past the consumed span, and continues. Within a single n-gram
length, ties are broken by insertion order of the index, so the caller controls
precedence by build order.

Each n-gram is tried twice: verbatim, then **depluralised** — trailing `s` or
`es` stripped from every word in the gram. This is what makes `marketing
managers` and `sales directors` resolve; a separate stemming stage would have
to run before phrase matching and would then corrupt company names.

A `PhraseEntry` may carry more than one `{ field, value }` pair, which is how a
combined title phrase yields two matches from one span.

## `lib/people/`

### `aliases.ts`

The tables from the task, verbatim, plus:

- Countries reuse the Events country vocabulary and its aliases (`uk` → United
  Kingdom, `us`/`usa` → United States, `deutschland` → Germany, `uae` → United
  Arab Emirates).
- `COMBINED_TITLE_PHRASES` — each entry emits **both** a department and a
  seniority: `marketing manager`, `sales director`, `vp marketing`, `vp of
  marketing`, `head of partnerships`, `product lead`, and the systematic
  cross-product of the two closed vocabularies (`<department> <seniority>` and
  `head of <department>`), so the table stays in sync by construction rather
  than by hand.
- `VERIFICATION_PHRASES` and `BOOLEAN_PHRASES` per the task's Stage 3 table.

### `vocabulary.ts`

`buildPeopleVocabulary(people)` — memoised at module level. Builds one
`PhraseIndex` from, in this insertion order (earlier wins ties at equal length):

1. combined title phrases (both fields)
2. verification and boolean phrases
3. seniority aliases
4. department aliases
5. country aliases and `SELECT DISTINCT country`
6. `SELECT DISTINCT company`
7. `SELECT DISTINCT title`
8. `SELECT DISTINCT city`
9. `SELECT DISTINCT source`

Company before title before city matters: `NovaAI Systems`, `CloudForge Ltd`
and `Medidata Europe` must win over any single word inside them, and
longest-first already guarantees that against shorter entries.

### `parseQuery.ts`

```ts
export function parsePeopleQuery(input: string, vocab: Vocabulary): ParsedQuery
// ParsedQuery = { filters: PeopleFilters, matched: Match[], unmatched: string[] }
```

Pure, synchronous, no I/O, never throws. Input capped at 500 characters.

**Stage 1 — normalize.** `normalize()` then `tokenize()`. Every later stage
operates on this single token array and consumes token spans from it; there is
no re-parsing of raw text downstream.

**Stage 2 — numeric conditions.** `scanNumericConditions` against two field
specs (`confidence`, and `score` with the alias `platform score`). Handles
`%`, `+`, `>`, `>=`, `<`, `<=` and above / over / more than / at least /
greater than / below / under / less than / at most, plus `between X and Y`.
The bare-adjective forms are separate phrase entries: `high confidence` →
`confidenceMin: 85`, `low confidence` → `confidenceMax: 60`, and `top rated` /
`starred` / `high score` → `scoreMin: 90`. Matched spans are consumed.

Runs **before** phrase matching so the word `confidence` in *"confidence above
80"* is eaten by the numeric scanner rather than surviving to keywords.

**Stage 3 — boolean flags.** Verification and contactability phrases, consumed.
`needs verification` / `unverified` / `not verified` set **both**
`needs_verify` and `unverified`, per the task.

Verification and contactability are independent, and the longer phrase wins:
`verified emails` sets `verification: ['verified']` **only** — it does not also
set `hasEmail`, because the whole two-word span is consumed by the verification
entry before `email` can be read as a contactability signal. `with email` sets
`hasEmail: true` only. This is the behaviour the `c-level in india with
verified emails` test asserts.

**Stage 4 — phrase match.** `matchPhrases` over the remaining tokens, 4-gram
first. This is the stage that must run before keywords — the Events bug where
`united kingdom` fell through as two separate keywords is exactly this ordering
failure.

**Stage 5 — stopword removal** from what remains.

**Stage 6 — fuzzy rescue.** Single tokens only, against the 1-gram entries of
the vocabulary. Accepted when Levenshtein distance ≤ 2 **and** ≤ 25% of the
token's length. Single-token rescue is sufficient for the multi-word cases:
`markting managrs germny` rescues `marketing` (distance 1 of 9), `managrs` →
`manager` (1 of 7) and `germny` → `germany` (1 of 7) independently, and
`marketing` alone maps to department Marketing while `manager` alone maps to
seniority Manager. No fuzzy phrase matching is needed.

**Stage 7 — leftovers to keywords.** Whatever survives, deduplicated, capped at
3, also returned as `unmatched`.

### `filters.ts`

Mirrors `lib/events/filters.ts` exactly in structure:

- `parsePeopleQueryState(search)` / `serializePeopleQueryState(state)` — URL is
  the single source of truth shared by sidebar and search panel. Params:
  `country`, `city`, `company`, `title`, `seniority`, `department`, `source`,
  `verify`, `keyword` (repeatable); `confmin`, `confmax`, `scoremin`,
  `scoremax`; `email`, `phone`, `li` (`1`/`0`, absent = null); `q`, `sort`,
  `page`.
- `buildChecks(filters, search)` — one predicate per dimension, returning
  `null` for an unconstrained dimension.
- `filterPeopleList(people, filters, search)`.
- `computePeopleFacets(people, filters, search)` — counts each dimension
  against every check **except its own**, so opening "Country" still shows
  every reachable country. Same hold-one-out approach as
  `computeEventFacets`.
- `sortPeople(people, sort)` — `score` (default, descending), `confidence`,
  `name` (A–Z), `fetched` (most recent first). All sorts break ties on `id` so
  paging is stable.

### `searchIndex.ts`

Module-level array loaded from the seed at first access and cached across
requests; `revalidatePeopleIndex()` clears it for a future import path.
`queryPeople({ filters, search, sort, page })` → `{ results, total }`,
paginated at 50 with the true total returned separately.

### `chips.ts`

`buildPeopleFilterChips(filters, search)` → `{ id, label, value }[]`, and
`removePeopleFilterChip(filters, search, chipId)`. Structurally compatible with
`QueryChip` in `components/search/filter-chips.tsx`, matching
`lib/events/chips.ts`. Numeric chips read `≥ 80%` / `≤ 50%` / `70–90%`;
tri-state chips read `Has work email` / `No work email`.

## API — `app/api/people/query/route.ts`

```
POST { prompt: string, filters?: PeopleFilters, sort?: string, page?: number }
200  { filters, matched, unmatched, results, total, tookMs }
```

A thin controller over the pure modules: `validateBody()` with a Zod schema in
`models/people-query.ts`, then `parsePeopleQuery` + `queryPeople`, then
`jsonOk`. No tenancy — like `/api/companies`, this is a shared discovery
dataset, not workspace data. Uses `UnauthorizedError` conventions from
`lib/http/errors.ts` if auth is later added.

No `fetch` to any external service. No `answer` field. No reference to
`ANTHROPIC_API_KEY` anywhere in the path.

### Bulk bar

to Sequence, Merge and the `N selected` counter, and adds **Select all N
matching**. Selection is held as `{ mode: 'page' | 'all', ids: Set<string> }`
so "all matching" survives paging and applies to the filtered set rather than
the loaded page. Changing any filter clears the selection.
